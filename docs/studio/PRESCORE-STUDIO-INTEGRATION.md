# Prescore Studio · интеграция

## ADMIN и доступ

Основной проект использует Next App Router. До пакета маршрут `app/admin/page.tsx` отвечал `notFound()`. В dev-режиме `PRESCORE_STUDIO_INTERNAL=1` открывает внутренний пункт ADMIN → Prescore Studio. На странице и в обработчике всех ресурсов и команд проверяется реальная серверная сессия `getAuthSession` с ролью ADMIN. При production-сборке оба маршрута закрыты независимо от флага. Для полной интеграции в dev требуются настроенные основные Auth и БД. На Node 22.13 при необходимости передайте `NODE_OPTIONS=--experimental-strip-types` процессу Next.

Автономный preview работает на отдельном loopback-порту. Он проверяет право чтения/записи локального каталога ОС через подтверждение запроса браузера. Случайная HttpOnly/SameSite-кука привязывает конкретный браузер к подтверждённому запросу. Новый процесс требует новой сессии. Команды изменения проверяют origin и формат JSON. Оба способа входа используют один серверный обработчик Studio. В preview доступны только подготовленные синтетические источники. У команд отсутствуют параметры URL внешних сервисов, рабочих досье, платежей и ролей.

## Движок и границы конфигурации

`buildCanonicalCreditAnalysis(input, experiment?)` принимает внутренние, построенные компилятором зависимости текущего запуска. По умолчанию вызываются исходная формула и штатные реестры. Выражение применяется в `analyzeFinancialPeriod` до адаптации RiskFact. Зависимости из одного баланса проверяет стандартная обработка пропусков и качества Financial Analysis. Расчётная арифметика остаётся Number, как в действующем показателе. Формула использует собственную ограниченную грамматику только для этого показателя. Выполнение скриптов и доступ к ресурсам отсутствуют.

Изолированные правила используют штатную numeric-фабрику и evaluateRiskFacts. Реестр рекомендаций проходит validateRecommendationRegistry. Один и тот же экземпляр передаётся в Recommendations, проверку Action Plan и Explainability. Даже в эксперименте сверяются fingerprint реестра, происхождение и текст действий. Версия контракта правила читается как в продукте, отдельный SHA-256 фиксирует методологию черновика. Результат полноценного canonical-вызова хешируется целиком. Для интерфейса сохраняется проекция релевантных итогов, причин и источников. Пользовательские правки не применяются к готовым числам.

CPU-расчёт выполняется в отдельном Node Worker. При отмене он завершается. Порядковый номер запроса на клиенте защищает новую ревизию от запоздавшего ответа. Хеш реализации включает базу, версии расчётного контура и изменившиеся программные владельцы. Для отдельной новой базовой ревизии нужно пересобрать привязку совместимости и заново проверить эталоны и примеры.

## Хранилища и воспроизводимость

| Объект | Реализация |
|---|---|
| Архитектурный реестр | Версионированный атлас в studio/data/atlas.json.gz. graph.mjs сохраняет ID и собирает 22 области. Для RELATED/EVIDENCE поле executable равно false. Направленные расчётные связи снабжены источником, типом, единицей и временем. На карте отображаются возможные связи. Трасса запуска фиксирует конкретные оценки. |
| Методология и сценарий | Разные части неизменяемой записи версии. Пять значений, флаги источников и ID компании восстанавливают снимок из фиксированных синтетических материалов. Номер ревизии и SHA-256 методологии отделены от хеша данных. |
| Запуски | Отдельные записи runs. UUID, время, владелец, компания, версия, выбор оси сравнения, конфигурация, canonical input fingerprint, хеши исходных результатов, asOfDate, трасса и ошибки. |
| Сохранённые версии | FileStudioStore, каталог по хешу внутреннего владельца. Записи создаются атомарно с уникальными ID без замены предшественника. Два открытых черновика сохраняются отдельно. |
| Раскладка и комментарии | Разные ключи localStorage конкретного браузера. На методологию и пакет изменений не влияют. Перенос на другое устройство требует отдельного адаптера. |

Серверный адаптер предоставляет put, get и versions. Для командной работы нужен адаптер БД с полями owner/tenant, отдельными версиями, неизменяемыми snapshots, политикой хранения и проверкой полномочий на каждый запрос. Локальное файловое хранилище предназначено для одного владельца машины.

## Подготовка к применению

Контракт перехода — DRAFT → VALIDATED → REVIEWED → APPROVED_FOR_INTEGRATION. В этой версии валидированный пакет содержит базу, хеш методологии и сборки, данные, настройки, затронутые результаты, хеши двух расчётов, зависимости, поле утверждения и условие возврата. Импорт проверяет строгую схему и контрольную сумму, проверяет компилятором настройки и открывает черновик. Контрольная сумма защищает от случайного изменения. Подпись владельца и полномочия на утверждение требуют отдельной реализации.

Для активации понадобятся внутренний review с журналом, подписанные решения, привязка версии к рабочему досье, миграции, матрица регрессии и отдельный release gate с откатом. Рабочие политики, сохранённые заключения и release gates этого проекта не переключались.
