## Prepared behavior

Password login → native Better Auth TOTP/one-use backup-code challenge → existing session → database proof for that session → existing `getAuthSession` → effective roles → all existing API/page permission checks. A database ADMIN role alone does not pass the `required` mode. The proof expires after 12 hours or with the session; a new session needs its own proof. Sensitive factor management also requires the current password and a factor verified within five minutes. Native trusted-device/session-disable bypass options are refused. Native factor disabling is not exposed as a password-only recovery shortcut.

The owner configures TOTP and receives encrypted-at-rest recovery codes through `/prescore-control/security`. Codes and the setup key are displayed only in that secure interface and held in component memory, never in browser navigation URLs, localStorage, audit events, screenshots or GitHub. The native enrollment response contains the authenticator URI; it is parsed locally in the component, not opened or sent to an external QR provider. The owner must save the codes in their own secure store and verify the factor. Login and re-verification accept a single-use backup code. Password reset revokes sessions but does not remove or bypass the factor.

`PRESCORE_ADMIN_2FA_MODE` has three explicit modes:

| Mode | Behavior | Allowed phase |
|---|---|---|
| `disabled` (current default) | Existing login behavior; no MFA schema queries or plugin endpoints; security screen states that protection is not enabled | Existing live staging, until the approved execution gates are satisfied |
| `enrollment` | Native factor setup enabled; unenrolled ADMIN retains existing access temporarily; enrolled ADMIN needs session proof | Approved, supervised enrollment window only; never final acceptance |
| `required` | ADMIN omitted from effective roles until setup and session verification succeed; other existing CLIENT/BROKER rights remain unchanged | Final approved staging mode |

Invalid modes fail configuration. Missing factor/proof schema fails closed when active. The existing ADMIN-only page is not the enforcement boundary: billing administration, foreign dossier/document access, admin reads/writes and other consumers all obtain the same filtered server roles. No real user's stored role or broker assignment is changed.

## Recovery boundaries

- Lost authenticator, backup code available: owner uses “Нет приложения — резервный код” in the same login flow. One code is consumed; it establishes proof only for the resulting actual session. After a fresh factor confirmation and password check, the owner may replace the backup-code set in the secure UI. Existing codes become invalid.
- Lost both factors: do not disable enforcement globally, grant a replacement ADMIN or accept email/password reset as second-factor proof. After separately authorized operator identity verification, quiesce writes for the affected account and make a fresh verified recovery point. In one reviewed transaction, reset **only that existing user's** factor enrollment/material and revoke all their sessions (cascading their proofs); keep their identity/roles/analyses unchanged. Record a non-secret recovery event. Keep mode `required`; the owner can sign in, but cannot regain ADMIN authority until private re-enrollment and verification. Exact user selection and affected-row counts must be reviewed before this exceptional operation; no broad reset command is supplied here.
- Runtime defect after enrollment: keep the additive schema and factor data. Use a compatible recovery build with enforcement intact or temporarily restrict administrative access while fixing the defect. Do not turn off the factor or downgrade to the old password-only build as an automatic rollback. A disaster restore is a separate approved operation, preserving subsequent data and encrypted-factor configuration; it is never the isolated restore test above.
