## Получение пакета без действий владельца

1. Прочитать действующие инструкции репозитория и этот документ.
2. Использовать Files для получения полного пакета по указанному file_id. При необходимости найти точное имя в папке `/Prescore/Approved_Client_v1/` на поверхности Library.
3. Для программного доступа к Library-файлу вызвать `files.materialize` с `raw_file`, например:

```json
{
  "items": [
    {
      "file_ref": {"file_id": "file_0000000073588212b74b83e9a023c36b"},
      "outputs": [{"representation": "raw_file"}]
    }
  ],
  "destination": {
    "directory": "/mnt/data/prescore-client-approved",
    "conflict_policy": "dedupe"
  }
}
```

Использовать путь, фактически возвращённый инструментом. Путь Библиотеки не является путём контейнера. Если инструменты называются иначе, сначала прочитать их актуальную схему; не выполнять этот пример как shell-команду.

4. Проверить SHA-256 архива, затем распаковать в отдельную папку, не поверх рабочего дерева. Не исполнять содержимое архива при распаковке.
5. Прочитать `WORK_TASK.txt` полностью. `reference/README.md` содержит границы прототипа, `MANIFEST.json` — контрольные суммы.
6. Открыть `reference/Prescore_Client_Preview.html` в разрешённом браузерном preview и пройти все девять разделов. Изображения использовать как дополнительные ориентиры.
7. Продолжить реализацию по полному WORK_TASK.txt от актуального HEAD `prescore-product-v1`, а не от исторического SHA из переписки.

Если текущему Work не предоставлен доступ к этим Library-файлам, не создавать новый макет по описанию и не заявлять, что эталон просмотрен. Сообщить конкретный отсутствующий доступ. Пакет можно найти также по названию и каноническому Library ID; обходить ограничения доступа нельзя.

## Неизменные условия задания

- Визуальное направление утверждено владельцем. Перенести его в существующий Prescore, а не создавать новый дизайн или ещё один автономный прототип.
- Сохранить композицию, типографику, графики, таблицы, переходы и мобильную версию всех девяти разделов.
- Использовать реальные React-компоненты проекта и существующие canonical-модели и серверные API. Не встраивать весь HTML через iframe и не создавать второй Credit Engine.
- Учебные компании, суммы, Index, ставки, localStorage и действия прототипа не являются production-данными или готовой серверной интеграцией.
- Существующую и параллельную работу по дебиторке сохранять. Не создавать второй реестр или импортёр.
- Промежуточные исходники сохранять доступными восстановительными пакетами. Проверять доступность их байтов, а не только наличие временной папки.
- Не изменять кредитную методологию ради визуала.
- Не публиковать на Amvera, staging или production без отдельного разрешения.
