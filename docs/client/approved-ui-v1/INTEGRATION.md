# Утверждённый клиентский кабинет

Обычный маршрут клиента — `/dashboard`. Девять разделов используют React-компоненты из `app/components/workspace/approved`. Оболочка, графики, таблицы, формы и выдвижные карточки общие с учебным стендом. Стенд собирается из `tests/approved-client/preview.tsx` отдельной командой. В приложение этот вход и его набор данных не импортируются.

Основа переноса — коммит `a46991d26c0fdb70aebb3f3fe55ce458a32872a3`. SHA-256 утверждённого HTML — `7031e80de0f3d9634f5a8ca8daa01e6ee603e32c0cab633901a28fcb4d790e15`. Инструкция получения пакета и его контрольных сумм находится рядом в README.md.

## Чтение, запись и границы разделов

Список разрешённых досье загружается из `/api/workspace`. Аналитика одной компании приходит из `/api/workspace-model?analysisId=…`. Обзор, кредитный профиль и план читают один полученный серверный снимок. Параметр `bankMonth` ограничивает только банковские потоки. Роль, состав досье и тариф проверяет сервер. Переключатель фокуса влияет только на подсказки.

| Раздел | Реальные данные и период | Сохранение | Проверка и ограничение |
|---|---|---|---|
| Обзор | Деньги и внешние потоки из basic.bankingFacts, заключение, Index и Capacity из full.report. Остаток хранит свою дату | Переход к созданию черновика | Index совпадает с API и кредитным профилем. BASIC видит доступные банковские показатели |
| Финансы | Месяцы выписок, баланс и внешние списания. Годовая и промежуточная БФО из financialAnalysis со своим отчётным периодом | Импорт через «Документы» | Выбранный месяц переживает reload. Загруженный квартал появляется в БФО. Категории образуют круг только при сверке с суммой списаний |
| Кредитный профиль | Канонические заключение, компоненты Index, ограничения и обязательства. Основной долг БКИ показывается для идентифицированной компании-заёмщика на дату отчёта | Переходы к плану, источникам и действующему подробному анализу | Известный ноль, чужой субъект, неполные данные и BASIC проверяются отдельно. У партнёра просмотр |

## Визуальная проверка

Исходные сетка, типографика, навигация, карточки, цветовые токены и мобильный порог 850 px перенесены из HTML. Стили ограничены контейнером кабинета. Из разделов доступны имеющиеся подробные отчёты, портфель, записи по документам и «Спросить Prescore». Реальные длинные названия, состав источников и длина заключения меняют высоту карточек. Суммы, для которых краткая запись в миллионах потеряла бы копейки, показаны в рублях. Графики дополнены доступной таблицей и текстом о недостающем ряде. Рекомендации без контракта изменения статуса открываются для чтения. Учебный баннер виден только в автономном файле.

В восстановительном ZIP папки qa/reference и qa/candidate содержат попарные снимки исходного HTML и нового React-стенда на одинаковом досье. Папка qa/integrated содержит снимки защищённого /dashboard с учебными банковскими выписками и квартальным документом, сохранёнными в изолированной PostgreSQL. В каждой папке есть все девять разделов при 1440 × 1100 и 390 × 844. В qa/integration.json и qa/screens.json записаны результаты браузерных проверок.

## Воспроизведение

1. В рабочей копии выполнить `npm ci` и `npm run build`.
2. Для автономного просмотра выполнить `node scripts/qa/approved-client-preview.mjs ./Prescore_Client.html`. Сохранённый HTML можно открыть двойным щелчком. Для снимков запустить `node scripts/qa/approved-client-visual.mjs путь/к/reference/Prescore_Client_Preview.html ./Prescore_Client.html ./qa` с установленным Chromium Playwright. Путь к системному Chromium можно передать через QA_CHROMIUM_PATH.
3. Для серверной проверки поднять приложение в стандартном RC-окружении из scripts/release/ci-environment.mjs на 127.0.0.1 с отдельной локальной PostgreSQL prescore_rc*, выполнить scripts/platform/db-migrate.mjs, включить тестовую почту и тестовый биллинг. Затем выполнить `node --experimental-strip-types scripts/qa/approved-client-integration.mjs ./qa`. Проверка создаёт только учебные учётные записи в этой БД.
4. Предметную проверку БКИ запустить командой `node --experimental-strip-types --test tests/approved-client/principal.test.mjs`. Остальные проверенные наборы перечислены в qa/verification.txt итогового пакета.

## Отдельная последующая публикация

1. Получить разрешение на конкретный целевой контур. Сверить SHA кандидата, актуальные HEAD продукта и staging и изменения по дебиторке. Если ветки разошлись, сначала перенести согласованные коммиты в интеграционную ветку и повторить сборку и QA на полученном SHA.
2. Для разрешённого staging опубликовать проверенный коммит через обычное слияние в ветку staging. Существующий workflow amvera-staging-rc3.yml запускается при push в неё и передаёт сборку в Amvera. Дождаться завершения workflow и запуска приложения.
3. Проверить /api/ready, опубликованную версию и защищённый /dashboard в браузере. На тестовой компании проверить выписку, БФО, сохранение черновика, права и мобильное меню. Сопоставить с qa/integrated.
4. Перед production отдельно согласовать целевой релиз, доступы и откат к предыдущей версии. Этот перенос заканчивается сохранением в продуктовой ветке.
